# Issue 16 — Proposed Solution

## Executive Summary

Port only the reminder configuration, interval-neutral wording and focused tests onto **fresh upstream main**, preserving upstream's five-minute default and reminder lifecycle. Do not merge a fork branch or directly reuse the historical proposal. This is fork planning documentation, not part of the upstream contribution.

Use a small parser and focused configuration tests, reusing upstream's existing lifecycle suites rather than duplicating a tool-by-interval matrix. Retain the environment-only, silent-fallback contract **unless the human explicitly amends issue 16**; recommendations about diagnostics and prior upstream discussion below are not accepted requirements. This revision is not merge-ready or authorization to implement or publish upstream.

No ADR is needed: runtime-owned timer and authorization boundaries remain unchanged. Execution is specified in [the Implementation Plan](16-implementation-plan.md).

### Contract and compatibility

1. Add a pure `reminderIntervalMs(raw: string | undefined): number` parser and a production environment reader in `src/reminders.ts`. Keep it to trimming, ASCII `[0-9]+`, numeric conversion and inclusive range validation; that range also rejects unsafe numbers without needing a separate parser framework. Accept leading zeros and values `1`–`35791`. Explain the bound in a short code comment and README: `floor(2147483647 / 60000) = 35791`; `35791 * 60000 = 2147460000` ms, whereas `35792 * 60000 = 2147520000` exceeds Node's signed 32-bit timeout ceiling (overflow can schedule about 1 ms, not the requested delay). A 1440-minute cap is easier to remember but unnecessarily excludes currently valid values; recommend retaining 35791. Choosing the alternative needs an explicit issue amendment: “Accept whole minutes 1–1440 inclusive; larger values use the five-minute default, without clamping,” with corresponding docs/tests. Missing/blank/zero, signs, fractions, exponents, nondecimal forms, suffixes, non-ASCII digits, unsafe and out-of-range values silently return `300000` ms. Never clamp, disable, throw for these strings, or emit raw input.
2. Retain upstream's exported `REMINDER_INTERVAL_MS = 300000` as the default, rather than renaming/removing it. Extend `CoordinatorReminders(host, clock?)` with an optional third validated `intervalMs` argument defaulting to that constant. Direct two-argument consumers remain compatible. The scheduler receives only milliseconds, not environment input; change its delay operand, not its state machine.
3. Add optional `RuntimeOptions.reminderMinutesEnv?: () => string | undefined` as a deterministic test seam; production reads `process.env.PI_INTERCOM_REMINDER_MINUTES`. Capture and parse exactly once inside `Intercom.start()` after its active-runtime guard, inside existing startup error handling and before the first asynchronous startup step. Hold the number in a start-local constant passed into the timer. Construction, resets, stop/rearm and config-only `reload()` do not reread; close/start or a new runtime does. Startup stays disarmed. Shared runtime code may snapshot a worker's own environment too, but workers gain no reminder authority. Do not add launcher propagation, filtering or shared settings.
4. Preserve all qualifying-call checks and arm-before-effect ordering, including failures after valid initiation. Preserve invocation/revision/generation/tick fences, coordinator rechecks, busy skipping without backlog, owning-run abort, explicit stop/next-call rearm and lifecycle disposal. Incoming messages/reports/status, list/status reads (including probes), invalid or unauthorized calls and bookkeeping do not arm/reset.
5. Change only “every five minutes” to “at the configured interval” in the fixed reminder; keep every authority sentence unchanged. Make the stop-tool description interval-neutral without changing permissions or effects. README's current behavior text/quoted reminder must agree; historical release notes need not be rewritten or expanded.
6. README documents bounds, silent fallback categories, zero not disabling, POSIX/PowerShell launch examples, no settings.json or disk/wire changes, process-only scope and restart semantics. A child-shell export cannot update its running parent. Pi `/reload` rereads that process's existing environment; changing inherited operator values requires restarting Pi with the new environment. `intercom_reload_worker` is config reload only.

### Review recommendations and human choices

- **Startup diagnostic — recommend an amendment, not silent adoption.** Petro is right that privacy does not require silence: `10m`/`0` typos are hard to diagnose. Prefer one value-free, nonfatal coordinator startup notification for explicitly supplied, nonblank invalid input. No notification for unset/blank input, workers, resets/rearms or config reload; no timer arming. Keeping silence avoids extra startup output and preserves fork compatibility, but hides mistakes. Human choice **D1**: retain the current silent fallback, or approve this replacement wording in issue 16: “Unset/blank input uses the five-minute default silently. Other invalid input uses that default and emits at most one best-effort coordinator notification per runtime start: `PI_INTERCOM_REMINDER_MINUTES is invalid; using the 5-minute default`. Notification failure must not block startup or worker operations; never echo raw input.” The parser remains pure; if approved, retain validity alongside the single snapshot and notify only after coordinator identity is known, under existing lifecycle checks. Add invalid/valid/absent/worker and failed-notify assertions. Until agreement is recorded, implement neither this notification nor a changed parser result API.
- **Environment versus flag — recommend env-only for this port.** Upstream's `registerFlag('intercom-root', …)` is a real configuration precedent, but asserts workspace authority; this knob is a process-local timing preference. The named environment variable preserves fork operator compatibility and works without adapter/CLI changes. A flag improves CLI discovery but needs registration, startup plumbing and, if both exist, precedence/validation semantics. Explain that trade-off in the future upstream PR; a flag is a maintainer discussion option, not an authorized second input. No new decision is needed to retain env-only. If the human prefers a dual-source alternative, proposed wording (unaccepted) is: “Read `--intercom-reminder-minutes` once at runtime start; when supplied, it takes precedence over the environment even if invalid, using the same parser/default policy. When absent, use `PI_INTERCOM_REMINDER_MINUTES`.” That choice would require adapter registration/startup tests and an issue amendment before implementation; a flag-only switch would additionally remove existing env compatibility and is not recommended.
- **Prior upstream discussion — recommend permission to ask first.** A short “configurable reminder interval: env or flag; silent fallback or value-free warning?” issue could prevent wasted implementation. Current acceptance says a separate issue is opened **only if required**, and no upstream publication is authorized. Human choice **D2**: retain that policy, or approve: “After explicit publication authorization, open a short upstream design issue before coding unless an existing maintainer answer settles these questions; follow current upstream guidance and record the answer. Any incompatible maintainer request returns for agreement in issue 16.” An unanswered discussion is not agreement and does not authorize implementation. Read-only compatibility analysis can continue while D1/D2 are pending.
