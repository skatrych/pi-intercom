### Contract and compatibility

1. Add a compact pure parser and a production environment reader in `src/reminders.ts`. Return the interval plus only the validity metadata needed for D1, for example `{ intervalMs: number; invalidInput: boolean }`; retain no raw input in the result. Keep parsing to trimming, ASCII `[0-9]+`, numeric conversion and inclusive range validation; that range also rejects unsafe numbers without a separate parser framework. Accept leading zeros and values `1`–`35791`. Explain the bound in a short code comment and README: `floor(2147483647 / 60000) = 35791`; `35791 * 60000 = 2147460000` ms, whereas `35792 * 60000 = 2147520000` exceeds Node's signed 32-bit timeout ceiling (overflow can schedule about 1 ms, not the requested delay). Retain 35791; a 1440 cap would exclude valid inputs and is not adopted. Missing/blank input returns `300000` ms without the invalid-input marker. Zero, signs, fractions, exponents, nondecimal forms, suffixes, non-ASCII digits, unsafe and out-of-range values return `300000` ms with that marker. The parser has no notification side effects. Never clamp, disable, throw for these strings, or emit raw input.
2. Retain upstream's exported `REMINDER_INTERVAL_MS = 300000` as the default, rather than renaming/removing it. Extend `CoordinatorReminders(host, clock?)` with an optional third validated `intervalMs` argument defaulting to that constant. Direct two-argument consumers remain compatible. The scheduler receives only milliseconds, not environment input; change its delay operand, not its state machine.
3. Add optional `RuntimeOptions.reminderMinutesEnv?: () => string | undefined` as a deterministic test seam; production reads `process.env.PI_INTERCOM_REMINDER_MINUTES`. Capture and parse exactly once inside `Intercom.start()` after its active-runtime guard, inside existing startup error handling and before the first asynchronous startup step. Hold interval and validity together in one start-local parsed snapshot; pass only its milliseconds into the timer. Construction, resets, stop/rearm and config-only `reload()` do not reread; close/start or a new runtime does. Startup stays disarmed. For marked invalid input, attempt at most one `host.notify` per coordinator runtime start with fixed text: `PI_INTERCOM_REMINDER_MINUTES is invalid; using the 5-minute default`. Notify only after coordinator identity is known and existing session/root/generation checks still pass, within the coordinator startup path, not shared `reload()` or the scheduler. Catch notification failure locally without echoing its error or input; it must not prevent startup or worker operations, trigger retries or arm/reset a timer. Unset/blank and valid input are quiet; workers (including anonymous workers), resets/rearms and config reload emit no invalid-input warning. Shared runtime code may snapshot a worker's own environment too, but workers gain no reminder authority. Do not add launcher propagation, filtering or shared settings.
4. Preserve all qualifying-call checks and arm-before-effect ordering, including failures after valid initiation. Preserve invocation/revision/generation/tick fences, coordinator rechecks, busy skipping without backlog, owning-run abort, explicit stop/next-call rearm and lifecycle disposal. Incoming messages/reports/status, list/status reads (including probes), invalid or unauthorized calls and bookkeeping do not arm/reset.
5. Change only “every five minutes” to “at the configured interval” in the fixed reminder; keep every authority sentence unchanged. Make the stop-tool description interval-neutral without changing permissions or effects. README's current behavior text/quoted reminder must agree; historical release notes need not be rewritten or expanded.
6. README documents bounds, fallback categories and the fixed value-free startup warning for explicit nonblank invalid input; unset/blank stays quiet. Document zero not disabling, warning failure being nonfatal, coordinator-only startup scope, POSIX/PowerShell launch examples, no settings.json or disk/wire changes, process-only scope and restart semantics. A child-shell export cannot update its running parent. Pi `/reload` rereads that process's existing environment; changing inherited operator values requires restarting Pi with the new environment. `intercom_reload_worker` is config reload only.

### Review dispositions

- **D1 — accepted startup diagnostic.** Captain requires the invalid-input warning and a value-free default-fallback statement. The contract above incorporates Petro's diagnostic suggestion without raw input, repeated notifications, timer effects or startup/worker-operation failures. Historical silent-fallback recommendations and approvals cover earlier snapshots, not this ruling-incorporation revision. Focused warning/quiet-path/failure/lifecycle assertions are in the plan; D1 is not an unresolved choice.
- **Environment versus flag — retain env-only.** Upstream's `registerFlag('intercom-root', …)` is a real configuration precedent, but asserts workspace authority; this knob is a process-local timing preference. The named environment variable preserves fork operator compatibility and works without adapter/CLI changes. A flag improves discovery but adds registration, startup plumbing and dual-source precedence/validation. Explain the trade-off in the future upstream PR; neither a flag nor changed bounds is adopted. An incompatible maintainer request returns for explicit agreement, not Developer discretion.
- **D2 — accepted: no upstream discussion required now.** Do not open or wait for a prior design issue or maintainer answer as an implementation prerequisite. No upstream publication is authorized in this round. After separate implementation/submission authorization and exact-tip verification, follow then-current required upstream guidance; create a prior issue only if that guidance requires it. The earlier optional-discussion proposal is superseded, not a pending decision.
