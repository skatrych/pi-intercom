# Issue 16 — Proposed Solution

## Executive Summary

Port only the reminder configuration, interval-neutral wording and focused tests onto **fresh upstream main**, preserving upstream's five-minute default and reminder lifecycle. Do not merge a fork branch or directly reuse the historical proposal. This is fork planning documentation, not part of the upstream contribution.

No ADR is needed: the existing runtime-owned, ephemeral timer and authorization boundaries remain unchanged. The non-trivial work is compatibility and regression coverage, not new component architecture. Execution is specified in [the Implementation Plan](16-implementation-plan.md).

### Contract and compatibility

1. Add a pure `reminderIntervalMs(raw: string | undefined): number` parser and a production environment reader in `src/reminders.ts`. Use JavaScript `trim()` then ASCII `[0-9]+`, numeric conversion and safe-integer/range checks. Accept leading zeros and values `1`–`35791`; the maximum delay is `2147460000` ms, below Node's `2147483647` timeout ceiling. Missing/blank/zero, signs, fractions, exponents, nondecimal forms, suffixes, non-ASCII digits, unsafe and out-of-range values silently return `300000` ms. Never clamp, disable, throw for these strings, or emit raw input.
2. Retain upstream's exported `REMINDER_INTERVAL_MS = 300000` as the default, rather than renaming/removing it. Extend `CoordinatorReminders(host, clock?)` with an optional third validated `intervalMs` argument defaulting to that constant. Direct two-argument consumers remain compatible. The scheduler receives only milliseconds, not environment input; change its delay operand, not its state machine.
3. Add optional `RuntimeOptions.reminderMinutesEnv?: () => string | undefined` as a deterministic test seam; production reads `process.env.PI_INTERCOM_REMINDER_MINUTES`. Capture and parse exactly once inside `Intercom.start()` after its active-runtime guard, inside existing startup error handling and before the first asynchronous startup step. Hold the number in a start-local constant passed into the timer. Construction, resets, stop/rearm and config-only `reload()` do not reread; close/start or a new runtime does. Startup stays disarmed. Shared runtime code may snapshot a worker's own environment too, but workers gain no reminder authority. Do not add launcher propagation, filtering or shared settings.
4. Preserve all qualifying-call checks and arm-before-effect ordering, including failures after valid initiation. Preserve invocation/revision/generation/tick fences, coordinator rechecks, busy skipping without backlog, owning-run abort, explicit stop/next-call rearm and lifecycle disposal. Incoming messages/reports/status, list/status reads (including probes), invalid or unauthorized calls and bookkeeping do not arm/reset.
5. Change only “every five minutes” to “at the configured interval” in the fixed reminder; keep every authority sentence unchanged. Make the stop-tool description interval-neutral without changing permissions or effects. README's current behavior text/quoted reminder must agree; historical release notes need not be rewritten or expanded.
6. README documents bounds, silent fallback categories, zero not disabling, POSIX/PowerShell launch examples, no settings.json or disk/wire changes, process-only scope and restart semantics. A child-shell export cannot update its running parent. Pi `/reload` rereads that process's existing environment; changing inherited operator values requires restarting Pi with the new environment. `intercom_reload_worker` is config reload only.

### Scope and limits

Expected upstream diff: `src/reminders.ts`, `src/runtime.ts`, one description in `src/index.ts`, README, focused reminder tests and normal-suite registration. Upstream ignores `dist/`; builds generate it locally, not as contribution files. No version/lockfile/release, adoption, launcher, monitor, config-schema or dependency changes; no production installation or live-host probe. These two planning documents stay in the fork. No implementation/test execution or publication is claimed by this design round. If freshly fetched upstream changes invalidate the contract or boundaries, return the concrete incompatibility to Coordinator rather than silently redesigning requirements.
