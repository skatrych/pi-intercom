# ADR 0009-A: First-declaration authorization is an explicit local UI decision

- Status: Proposed; implementation pending review
- Date: 2026-10-18
- Scope: [skatrych/pi-intercom #9](https://github.com/skatrych/pi-intercom/issues/9), refined issue body
- Inspected base: `main@1d5bb074fa3fe306f394c1a292cbed95ff438f3b`
- Related: [visible prompts](0009-adoption-prompt-visibility.md), [Git isolation](0009-first-declaration-git-safety.md), [implementation plan](0009-adoption-ux-implementation-plan.md)

## Context

`AdoptionWorkflow.bootstrap` already requests `boardInitialize`, then `askAuthority` requests a typed reference. `decide` in state (b) with no claim requests only that reference. These cases establish first authority; they do not replace another coordinator. The extra text question is redundant in (a), but deleting it without replacement in (b) would remove its only explicit decision.

`parseClaim` requires nonempty bounded `authority.record` and `authority.wording` (maximum 2000 characters; no control characters), first-declaration `confirmedEndedAt: null`, active phase, no predecessor/intent, and identical before/after config hashes. No schema change is necessary. Existing-board adoption is a different transition with intentionally stronger human gates.

## Decision

### First declarations only

1. State (a), no board and no claim history: enrich the existing `boardInitialize` yes/no. Show the canonical projects-home root, verified **full** current session ID and bound port, board/config creation, root claim generation and claim-only Git commit, and that readiness opens only after committed evidence and local promotion. Do not add a second authorization question.
2. State (b), existing board already naming this verified session and no claim history: introduce `firstCoordinatorDeclaration` yes/no with the same context, explicitly saying that config is not replaced; a declaration claim is generated and committed. No `authorityRecord` or `endedWording` input occurs in either first-declaration path.
3. Only `true` returned by this invocation's captured local Pi UI creates declaration authority. No/dismissal is a named `CANCELLED` result identifying first-board initialization or first-coordinator declaration. Invocation, a model message, a parameter, persisted text, silence, or an earlier answer is not consent.
4. Build private in-memory declaration evidence only after yes, for this survey/identity. Consume it in this invocation's existing bootstrap/declaration transaction; never expose it as a bridge parameter, serialize a reusable consent token, cache it across runs, or regenerate it for a changed preview. Keep the existing snapshot and identity checks under the all-writer lock. A stale decision halts; the human explicitly invokes again.

### Generated evidence, unchanged claim schema

Use a declaration-specific internal type/helper, separate from adoption's typed `Authority`; do not manufacture a termination timestamp for a declaration. Render the existing schema with:

- `kind: "first-coordinator declaration"`, `confirmedEndedAt: null`;
- a generated record explicitly saying that a human confirmed this first-coordinator declaration in this session's captured local Pi UI, **not** that the human typed this text or supplied an external reference;
- a nonempty generated `wording` describing the explicit yes/no decision, not `ENDED_WORDING`;
- the existing claim `date` as the declaration date, `previous: null`, `previousRecordCommit: null`, `intentCommit: null`, active phase, identical config hashes, and unchanged roster/source rules.

For a bounded, deterministic record template, include `sha256(UTF-8 canonical boardRoot)`, full verified session ID and port, with wording such as:

> Human explicitly confirmed this first-coordinator declaration in the captured local Pi UI; boardRoot SHA256 <hash>; session <full-id>; port <port>. Implementation-generated evidence, not a typed external reference.

The claim's `boardRoot` stores the **full** canonical path; its `coordinator` stores the full pair. Label the hash as a hash, not as a path or external record. This representation avoids overflowing the unchanged 2000-character authority limit when a valid boardRoot is up to 4096 characters. The dialog still shows the complete path. Test the actual generated bytes with `parseClaim`, including maximum-length IDs/paths; do not truncate contextual values silently. Existing schema-valid historical declarations remain valid, irrespective of whether their records were typed or generated.

### Existing-coordinator adoption remains strict

Retain the nonblank, bounded typed authority reference, exact termination wording, and separate explicit exact-transition confirmation. `ENDED_WORDING(target)` remains exactly:

```text
I confirm coordinator <full-target-session-id> ended
```

Do not trim, normalize case, accept approximations, prepopulate an input, or accept a programmatic answer for this gate. Human typing or pasting the exact sentence is accepted. Keep existing authority-reference trimming/validation; report cancelled/invalid reference as the **authorising record** step, without echoing its arbitrary contents.

The backend selects the target: configured old board coordinator for ordinary adoption; validated `intent.previous.sessionId` for supported prepared-before renewal. Label the target independently from current session, configured coordinator, and differing claim-record coordinator. A mismatched or empty termination answer reports **ended-wording confirmation**, the complete expected sentence, and the warning that disconnected/unknown does not prove termination. Cancellation names the input step. Never infer prompt rendering from receipt of an answer.

## Security invariants and consequences

- Keep role/mode/trust/idle/persisted-session validation, own endpoint identity, collision checks, old endpoint probe and under-lock re-probe, exact config bytes, claim-history/anchor checks, directory safety, all-writer locking and rechecks, one-use exact-transition consent, claim-only commits, promotion and action-readiness fencing.
- A malformed, deleted, newer, foreign, or uncommitted claim is not absence. State (b) alone is not eligibility: a matching claim-free survey and verified identity are required. A mismatched port still cannot open readiness or bypass existing identity/board validation.
- Input/confirmation refusals before effects write no config, claim or commits and trigger no worker action. Later Git/publication/promotion failures retain phase-specific evidence and existing recovery; never promise that nothing was written after those failures.
- The implementation observes an explicit UI yes, not proof of human attention or proof that the host displayed it correctly. Visibility has its own regression and manual verification requirement.

## Alternatives

- Keep typed first-declaration evidence but make it visible: rejected; retains redundant first-bootstrap authorization.
- Remove the state (b) record without a new yes/no: rejected; silently removes explicit consent.
- Remove adoption reference/exact wording or replace them with yes/no: rejected; outside scope and weakens a deliberate gate.
- Change claim schema or require full path repetition inside a bounded authority field: rejected; existing context fields plus a labelled root hash preserve schema and avoid a length trap.

## Verification

Implementation-plan AC1/2/5/6 cover both yes/no paths, absence of text input, schema round-trips, history refusal, stale decisions, exact wording, no-effect refusals and unchanged gate regressions. No implementation or live adoption was performed for this ADR.
